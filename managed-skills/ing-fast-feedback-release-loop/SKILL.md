# TestING: feedback → fix → update → native acceptance → next feedback

Operator decisions, 2026-09-21 and 2026-09-22. Canonical procedure: https://github.com/Wladefant/super-board/issues/191 . This is a working procedure, not an automated scheduler. Current operator instructions override historical workflow details within system/developer constraints.

## 1. Capture the concrete problem
- Answer where the operator wrote. State the observed problem, not a new program plan.
- Reuse dedicated issues, screenshots, source diagnoses, worker checkpoints and exact-source evidence. Recover stopped workers at their checkpoints; do not repeat completed inventories or unchanged-content reviews.
- Preserve original acceptance: actual Run for web application is not an Execute-page URL; recording readiness is not request acceptance; inspect generated evidence rather than merely checking existence.
- Ask only for genuinely missing decisions. If choice buttons fail, use a concrete plain-text Ja oder nein question and accept the reply.

## 2. Never stop independent acceptance for a bug
**Explicit operator correction, 2026-09-22: a bug must NEVER pause the whole acceptance program.**
- Keep one native laptop owner actively testing independent runnable scenarios while source owners fix defects in parallel.
- Block only the particular affected scenario/issue. Record its exact prerequisite, owner and resume point, then immediately execute the next independent acceptance case.
- Do not wait for all fixes, a combined release, or a phase boundary before testing unrelated functionality.
- After preserving evidence and obtaining applicable authorization, close a hung TestING instance safely and restart the normal application to continue unaffected checks. Do not repeatedly reproduce a known unchanged deadlock; avoid only that path until fixed.
- Once a fix is installed, rerun its original failed scenario and relevant regression paths. Close the issue immediately when all original criteria have evidence, not at the end of the entire matrix.
- Newest Windows issues, particularly the preceding two weeks, take priority. Defer operator-excluded macOS work without pretending it passed. Reuse existing complete evidence; many issues need verification/closure, not more implementation.
- A user actively testing has GUI priority. Pause conflicting clicks, focus changes, installation and shutdown, but continue read-only diagnosis and independent source work. Resume native operations on explicit handoff; do not turn a temporary ownership pause into a permanent global blocker.

## 3. Fix directly with bounded ownership
- Fetch the authorized GitHub remote and use the current integration tip. ING automation uses upstream; never fetch its private-PC-forbidden ADO origin. Verify the real engine Git root before engine work; a materialized subdirectory may resolve to the parent repository.
- Assign narrow independent source slices; preserve partial work. Only one worker operates the laptop GUI.
- Fix the source, not symptoms: no unrelated abstractions, arbitrary delays, warning suppression or fake success.
- Use focused original-scenario reproduction. UI changes require rendered interaction and visual evidence; compilation is insufficient.
- Flash changes receive one independent Flash review; changed content receives delta-only review. Astra changes do not receive an extra habitual independent review. Applicable CI and behavioral checks remain required.
- Integrate authorized passing changes with merge commits, never squash or rebase. Do not park verified fixes behind unrelated backlog.

## 4. Release focused updates
- Build from the exact integrated commit; rebuild affected Java/plugin artifacts and verify packaged code matches that source.
- Reuse the basis when runtime content is unchanged. Do not re-upload/retransfer a gigabyte basis for a plugin/tools fix. Normal upgrades must still align to the actual required basis/runtime version and preserve user data.
- Keep runtimes and third-party libraries out of normal updates and enforce actual size limits. An operator estimate such as 7 MB is not measured evidence.
- Publish immutable GitHub releases with source tag, German notes and normal installer/manifest/hash assets. Verify uploaded sizes and SHA256; preserve prior releases.
- Use existing package-script output; no extra manual staging/xfer folder or new package format.
- Required scripts must be automatically included through existing dependency inventory/closure and checked in the finished archive. A missing required source or archive entry must fail the build with its path, not become a tester surprise. Do not maintain divergent handlists or indiscriminately package secrets/developer artifacts.

## 5. Deliver and verify safely
- Explicitly authorized small updates may use the existing SSH connection. This narrowly overrides older blanket no-SCP rules; it does not authorize new tunnels, large basis transfers or arbitrary remote changes.
- Verify destination hash and use normal installer/target. No manual JAR substitution, runtime downloads, hidden launchers, scheduled tasks, WScript/cscript, EncodedCommand or SSO/profile resets.
- Coordinate install/close with the sole native owner. Preserve evidence, inspect process ownership and verify actual installed version. Never claim unsaved changes were saved when forced termination was necessary.
- Keep restored-existing-tester acceptance distinct from clean-new-tester acceptance. At the next clean-install test requested on2026-09-22, do NOT restore old local TestING projects/config/Autopilot/selections/browser state: exercise genuine first-time setup and OneDrive discovery. Preserve OneDrive, backups and unrelated OS/browser profiles. This does not remove normal upgrade data-preservation requirements.
- Use only specifically authorized real ADO test cases, actual plan/suite/point/configuration identities and dry-run where applicable; no hardcoded canary substitution. Configuration-suite and selected-case suite can legitimately differ. Never touch real ADO/Entra/Calimero from the private PC.
- Windows OpenSSH may terminate spawned children on disconnect. Use established visible supervised ownership and verify actual readiness/lifetime, not launcher exit or PID alone; never start duplicate short-lived Studios.
- Test actual browser actions and evidence contents. Directory inventories, daemon probes, fixtures, local UI, installed native proof and operator observations are different evidence classes. Physical passkey/MFA requirements block only that cell, not the rest.

## 6. Close and repeat
- Close only original-criteria-complete issues, immediately after proof. Merge/build/release alone does not prove installed behavior, paused continuation, cloud delivery or another user's access.
- Return a concise release link, exact installed/source version, proven fixes and remaining specific boundaries.
- Capture the next feedback without losing unresolved work. Repair that delta while the rest of acceptance continues; never invent redundant audits or stop the fleet for one defect.
